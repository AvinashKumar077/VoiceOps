# VoiceOps Intelligence Engine — API Reference for Frontend

VoiceOps ingests a CSV of customer reviews/conversations and turns it into a
structured product intelligence report: statistics, AI-clustered issues,
an executive summary, and (given two reports) trend analysis between two
time periods. This document describes the two HTTP endpoints the dashboard
needs to integrate against, their exact response shapes, and what each
field means.

There is no authentication layer yet — all endpoints are open.

## Running the backend locally

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Requires a `.env` file at the project root with:

```
LLM_PROVIDER=gemini        # or "openai"
GEMINI_API_KEY=...
OPENAI_API_KEY=...
LLM_MODEL=...              # optional, provider picks a sane default
```

Once running:
- Base URL: `http://localhost:8000`
- Interactive API docs (Swagger): `http://localhost:8000/docs`
- All routes are mounted under the `/api/v1` prefix.

## CSV input format

Both endpoints accept a CSV file upload. Column names are auto-detected
(case-insensitive), so exact headers don't matter as long as one column
per category is present:

| Purpose | Accepted header names (first match wins) |
|---|---|
| Review text (required) | `content`, `review`, `comment`, `feedback`, `message`, `text`, `description` |
| Rating (optional) | `score`, `rating`, `stars` |
| Id (optional) | `reviewId`, `id` |
| Date (optional) | `at`, `date`, `created_at`, `createdOn` |

Rows whose review text fails basic validation (empty/too short/garbage) are
silently dropped before analysis — so `statistics.total_reviews` in the
response can be lower than the CSV's row count.

## `POST /api/v1/upload`

Analyzes a single CSV and returns a full product intelligence report.

**Request:** `multipart/form-data`

| Field | Type | Required |
|---|---|---|
| `file` | CSV file | yes |

**Processing time:** proportional to review count — embeddings + clustering
+ 2 LLM calls (batch insights + executive summary). Expect roughly
30–60s for a few thousand rows on a typical dev machine. There is no
progress/streaming; the frontend should show a loading state for the
full duration of the request.

**Response:** `200 OK`, JSON body shaped as `ProductAnalysisReport`:

```json
{
  "executive_summary": { "...": "see ExecutiveSummary below" },
  "critical_issues": [ "...ClusterInsight objects..." ],
  "feature_requests": [ "...ClusterInsight objects..." ],
  "positive_feedback": [ "...ClusterInsight objects..." ],
  "statistics": { "...": "see DatasetStatistics below" }
}
```

### `ExecutiveSummary`

One paragraph-level, human-readable summary generated by a single LLM
call that also sees the dataset's rating distribution — so
`customer_health` reflects overall balance, not just the negative
clusters.

| Field | Type | Notes |
|---|---|---|
| `overall_sentiment` | string | Free text, e.g. `"Mixed to Negative"` |
| `customer_health` | string | Free text, e.g. `"Poor"`, `"Moderate with significant risk factors"` — **not an enum**, render as-is |
| `biggest_risk` | string | 1-3 sentences |
| `biggest_opportunity` | string | 1-3 sentences |
| `summary` | string | Longer narrative, 3-5 sentences — good candidate for the main dashboard summary card |

### `ClusterInsight`

One entry per detected issue/theme cluster. Appears inside
`critical_issues`, `feature_requests`, and `positive_feedback` — the
**same shape** in all three lists.

| Field | Type | Notes |
|---|---|---|
| `cluster_id` | int | Internal id, stable within one report only (not across uploads) |
| `title` | string | Short label, e.g. `"Core App Value with Paid Notification Friction"` |
| `summary` | string | 2-4 sentence explanation |
| `sentiment` | string | `"Positive"` \| `"Negative"` \| `"Mixed"` (LLM-generated, treat as free text) |
| `severity` | string | `"Low"` \| `"Medium"` \| `"High"` \| `"Critical"` |
| `business_impact` | string | `"Low"` \| `"Medium"` \| `"High"` |
| `engineering_effort` | string | `"Low"` \| `"Medium"` \| `"High"` |
| `recommended_priority` | string | `"P0"` \| `"P1"` \| `"P2"` \| `"P3"` |
| `affected_reviews` | int | Number of reviews in this cluster — **use this as the "N users" count** |
| `confidence` | float | 0–1, average cluster cohesion (similarity of reviews to the cluster centroid) — treat as a rough quality signal, not a business metric |
| `sample_reviews` | string[] | A handful of representative raw review excerpts, good for a "sample quotes" expandable section |

**How the three buckets are decided** (done server-side, no frontend logic
needed): sentiment decides the bucket first — `Positive` → `positive_feedback`,
`Negative` + `severity` in `{High, Critical}` → `critical_issues`, everything
else (including `Mixed` sentiment, or `Negative` with lower severity) →
`feature_requests`. So `feature_requests` is really "negative/mixed but not
urgent" — closer to a backlog than literal feature asks.

### `DatasetStatistics`

| Field | Type | Notes |
|---|---|---|
| `total_reviews` | int | Count *after* validation/cleaning |
| `average_rating` | float \| null | `null` if the CSV had no rating column |
| `average_review_length` | float | In characters |
| `min_review_length` | int | |
| `max_review_length` | int | |
| `rating_distribution` | object | Map of `"1"`–`"5"` (string keys in JSON) → count. Missing keys mean zero reviews at that rating — don't assume all 5 keys are present |

## `POST /api/v1/compare`

Runs the full `upload` analysis on two CSVs independently, then diffs the
two resulting reports to answer "what changed between these two periods?"
(e.g. last month vs. this month, v4.4 vs v4.5).

**Request:** `multipart/form-data`

| Field | Type | Required |
|---|---|---|
| `previous_file` | CSV file | yes — the *earlier* period |
| `current_file` | CSV file | yes — the *later* period |

**Processing time:** roughly double `/upload` (two full analyses) plus one
more LLM call — expect 60–120s+ for a few thousand rows per file each.

**Response:** `200 OK`, JSON body shaped as `TrendReport`:

```json
{
  "new_issues": [ "...ClusterInsight objects, only present in current..." ],
  "resolved_issues": [ "...ClusterInsight objects, only present in previous..." ],
  "growing_issues": [ "...Trend objects, sorted worst-first..." ],
  "shrinking_issues": [ "...Trend objects, sorted best-first..." ],
  "executive_trend_summary": "One paragraph of prose describing the overall trajectory."
}
```

### How matching works (for context, not something the frontend computes)

Insights from the two reports are matched to each other by semantic
similarity (embedding the title+summary of each insight and comparing via
cosine similarity, threshold 0.6) — not by exact title string — so
"Reminder Notifications Broken" in the previous report correctly matches
"Reminder Failure" in the current one. Anything in `current` with no match
in `previous` is a `new_issue`; anything in `previous` with no match in
`current` is a `resolved_issue`; matched pairs become `growing_issues` or
`shrinking_issues` based on whether `affected_reviews` went up or down.

### `new_issues` / `resolved_issues`

Same `ClusterInsight` shape as in `/upload` — see above. `new_issues`
existed only in the current period's report; `resolved_issues` existed
only in the previous period's.

### `Trend`

| Field | Type | Notes |
|---|---|---|
| `title` | string | Taken from the *current* period's insight title |
| `previous_reviews` | int | `affected_reviews` in the previous report |
| `current_reviews` | int | `affected_reviews` in the current report |
| `change_percent` | float | Signed, e.g. `+41.2` or `-19.0`, rounded to 1 decimal |
| `direction` | string | `"up"` \| `"down"` |

`growing_issues` is sorted worst-first (largest positive `change_percent`
first); `shrinking_issues` is sorted best-first (most negative
`change_percent` first, i.e. biggest improvement first).

### `executive_trend_summary`

Plain text, 3-5 sentences, generated by a single LLM call fed the full
diff (new/resolved/growing/shrinking). Good candidate for the top of a
"what changed" dashboard view. If nothing changed between the two periods
it will be the literal string `"No meaningful change detected between the
two periods."` instead of calling the LLM.

## Suggested dashboard layout

Mapping roughly to `ProductAnalysisReport` / `TrendReport`:

```
VoiceOps Dashboard
-------------------------------------------------
📊 Executive Summary       ← executive_summary.summary
❤️ Customer Health          ← executive_summary.customer_health
🔥 Critical Issues          ← critical_issues[]
💡 Feature Requests         ← feature_requests[]
⭐ Positive Feedback         ← positive_feedback[]
📈 Rating Distribution      ← statistics.rating_distribution
📋 Sample Reviews           ← *.sample_reviews[]
-------------------------------------------------
(Compare view, when two periods are selected)
🆕 New Issues                ← new_issues[]
✅ Resolved Issues           ← resolved_issues[]
📈 Growing Issues            ← growing_issues[]
📉 Shrinking Issues          ← shrinking_issues[]
🧾 Trend Summary             ← executive_trend_summary
```

## Known gaps / things not yet built

- No auth/API keys on any endpoint.
- No persistence — every call re-runs the full pipeline from scratch;
  nothing is stored server-side, so there's no "list past reports" endpoint.
  The frontend is responsible for holding onto report JSON if it wants
  history.
- No error handling has been built yet. A malformed/unparseable CSV, a
  file with no detectable review-text column, or any other backend
  failure currently returns **`500` with a plain-text body
  (`"Internal Server Error"`), not JSON** — there's no `detail`/error
  schema to parse. The frontend should treat any non-200 response as a
  generic failure and show a static error message; don't try to read a
  JSON body off of it yet. This is a known gap we intend to fix by
  wrapping the pipeline in explicit validation before Milestone 11.
- No progress/streaming — long-running requests are all-or-nothing.
